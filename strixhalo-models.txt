# =============================================================================
# Strix Halo cluster - model seed list
# =============================================================================
# Used by verify-and-seed-strixhalo-ai-server.sh (run AFTER setup + reboot).
# Run the seed on the SERVER node: /srv/models is exported read-only to the
# peer, so one download serves the whole cluster.
#
# Columns are whitespace-separated; '#' starts a comment line.
#
#   llm    <repo_id>  [dir-name]  [server|peer|distributed]  [options...]
#       -> the full Hugging Face model directory is downloaded into
#          /srv/models/<dir-name> and then registered in the shared catalog, so
#          it appears in the gateway's /v1/models immediately.
#          vLLM loads SAFETENSORS, not GGUF. Do not put .gguf repos here.
#          placement decides which node holds it:
#            server       resident on the head node        (default)
#            peer         resident on the worker node
#            distributed  split across BOTH nodes with Ray + RCCL over USB4
#                         (TP=2). Only worth it when the model cannot fit in one
#                         node's budget: the cable is ~13 Gbit/s, not NVLink, so
#                         a model that fits on one node is FASTER left there.
#
#          Trailing options are key=value, any order, all optional. A row
#          without them behaves exactly as before.
#            tools=<parser>   turn on OpenAI-style function calling with this
#                             tool parser. REQUIRED for agentic editor clients
#                             (Cline, Copilot Chat agent mode): without it vLLM
#                             never emits tool_calls and the client just sits
#                             there. See the parser note below.
#            reason=<parser>  reasoning parser. Without one, a thinking model's
#                             <think> block is delivered as ordinary content.
#            maxlen=<n>       cap the context window (--max-model-len).
#            keepwarm         exempt from idle eviction, so an editor session
#                             does not open with a multi-minute cold start.
#                             Still evictable under memory pressure, but only
#                             after every other resident model on that node.
#
#          PARSER NAMES ARE BUILD-SPECIFIC. They are a property of the vLLM
#          that actually got installed, not of any documentation, and an
#          invalid name makes vLLM exit during startup - which residencyd can
#          only report as "model failed". List the accepted names with:
#              sudo llm-model parsers
#          and check a failed start with 'journalctl -u vllm@<name>', which
#          logs the full argument vector.
#
#   comfy  <repo_id>  <path/in/repo>  <models-subdir>
#       -> /srv/comfyui/models/<subdir>/<basename>. That tree is exported
#          read-WRITE, so either node can download and both see the result.
#
# Duplicate weight formats inside a repo (original/, metal/, consolidated*,
# *.gguf, *.pth) are excluded automatically - they can easily double the
# download for files vLLM never opens.
#
# SIZING. Each node has ~128 GB unified memory, of which ~112 GiB is offered to
# models after the OS reserve and the runtime margin. Weights are only part of
# the cost: leave headroom for the KV cache, which grows with context length and
# concurrency. residencyd will refuse (HTTP 409) rather than thrash, so being
# optimistic here costs you a clear error, not a hung box.
#
# Sizes below are the ACTUAL download after exclusions, measured from the HF
# API. All repos here were checked to exist and be ungated unless noted.
# Uncomment what you want; the seed script prints the plan and asks first.
# =============================================================================


# ==============================  LLMs (vLLM)  ================================
# Served through the gateway on the head node, port 8000, OpenAI-compatible.

# --- Everyday driver: fast MoE, low latency -------------------------------
# gpt-oss-20b (21B total / 3.6B active). Small enough to stay resident next to
# something bigger, quick enough for agent loops and autocomplete. Kept as the
# always-available fallback while the Qwen models are being evaluated. ~14 GB
#
# This is the row marked 'keepwarm', which makes it the model an editor should
# point at: at ~14 GB it can sit resident permanently without crowding out a
# 52-67 GB model, so a coding session never opens with a cold start. Move the
# keyword to another row if you would rather keep that one hot instead.
llm    openai/gpt-oss-20b                     gpt-oss-20b            server  tools=openai maxlen=65536 keepwarm

# --- Newest generation: hybrid-attention Qwen (the set being evaluated) ----
# Qwen 3.6 and 3.8 share one architecture family. Three of every four layers
# use LINEAR attention and only the fourth is full attention, so the KV cache
# grows far more slowly with context than in a conventional transformer.
# All of them are natively multimodal (image + video in, text out) and ship a
# 1-layer MTP head, so vLLM can speculate against the model itself.
#
# Keep them in BF16, which is what the repos ship and what gfx1151 executes
# natively. Do NOT force --dtype float16: these weights are bfloat16-native
# and FP16 has a far smaller exponent range, so you buy overflow, not speed.
# Qwen also publishes -FP8 repackages of every model here. They are a trap on
# this box: RDNA3.5 has no FP8 units, so vLLM falls back to kernels that
# either refuse to load or emulate in software, losing the speed you
# quantised for. Half the download, none of the benefit.
#
# All three are 262144-token models. Do not serve them at full context - the
# KV cache allocation alone will eat the node, so every row below carries an
# explicit maxlen=. Raise it later if you have headroom; you can also edit
# MAX_MODEL_LEN in /etc/llm/models.d/<name>.conf and 'llm-model reload'.
#
# Every Qwen row sets tools=qwen3_coder. That is the tool parser Lemonade's
# vLLM integration applies to the whole Qwen3.* checkpoint family, and it is
# what makes function calling work for editor clients. VERIFY IT ONCE with
# 'sudo llm-model parsers' before trusting it - see the parser note in the
# header. Note that 'hermes' is NOT the right parser for Qwen3; it is for
# Nous Hermes fine-tunes.
#
# reason= is deliberately left unset. These are thinking models, so a
# reasoning parser would move the <think> block out of the reply body into
# reasoning_content - which is nicer. But a wrong parser name stops the model
# booting, whereas a missing one only makes the output untidy, so set it
# yourself after confirming the name with 'llm-model parsers'.

# Qwen3.6-35B-A3B (35B total / 3B active, 256 experts, top-8). The best match
# for this hardware in the list: MoE keeps only ~3B params active per token,
# so it streams ~6 GB per token off the LPDDR5X bus instead of the whole
# model, and it is the only vision-capable LLM here.                   ~67 GB
llm    Qwen/Qwen3.6-35B-A3B                   qwen3.6-35b-a3b        server  tools=qwen3_coder maxlen=65536

# Qwen3.8-27B (27B DENSE, newest weights here). Strongest answer per gigabyte,
# but dense means all 27B params are read for every token - roughly an order
# of magnitude more memory traffic than the A3B above. Expect single digit
# tokens/s. Worth it for hard one-shot reasoning, not for agent loops.
#                                                                      ~52 GB
llm    Qwen/Qwen3.8-27B                       qwen3.8-27b            peer    tools=qwen3_coder maxlen=32768

# Qwen3.6-27B - same architecture and same size as Qwen3.8-27B, one generation
# older. Both 27Bs sit on the PEER on purpose: that puts the A/B on identical
# hardware, and at ~52 GB each they cannot both stay resident inside the
# ~112 GiB budget, so residencyd swaps between them on demand. That is the
# intended behaviour, not a fault - a request for the idle one evicts the
# other. If you would rather have both hot at once, move one to 'server' and
# accept that it then competes with the 35B-A3B instead.               ~52 GB
llm    Qwen/Qwen3.6-27B                       qwen3.6-27b            peer    tools=qwen3_coder maxlen=32768

# --- Opt-in: models that NEED both nodes (placement=distributed) -----------
# These do not fit in one node's budget, so Ray splits them across the USB4
# link with tensor parallelism. Expect noticeably lower tokens/s than a
# single-node model - the interconnect is the bottleneck, and that is the
# trade you are making to run the model at all. Both nodes must be up.
#
# Qwen3-Next-80B-A3B-Instruct (80B total / 3B active).                 ~163 GB
#llm    Qwen/Qwen3-Next-80B-A3B-Instruct       qwen3-next-80b         distributed
#
# GLM-4.5-Air (106B total / 12B active) - excellent agentic model, but 12B
# active params over a 13 Gbit/s link is slow. Try it, measure it.     ~221 GB
#llm    zai-org/GLM-4.5-Air                    glm-4.5-air            distributed
#
# NOT LISTED, deliberately: Qwen/Qwen3.8-Flash-Next (~131B total / ~6B active).
# It is the MoE you would want, but the BF16 repo is over 330 GB on disk and
# the whole cluster only offers ~224 GiB of model memory, so it cannot be made
# resident even split across both nodes. The -FP8 repackage is 173 GB and
# would fit at ~86 GB per node, but gfx1151 has no native FP8, so expect it to
# fail to load rather than merely run slowly. Revisit if AMD ships FP8 support
# for RDNA3.5. Qwen/Qwen3.8-2.4T-A95B is out of reach by two orders of
# magnitude - do not try it.
